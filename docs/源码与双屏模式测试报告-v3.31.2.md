## 三、缺陷清单（3 项 + 1 观察）

### SYN-1【P2】双栏滚动映射坐标系混用 → 中后段滚动预览跳到文档尾

- **复现**（`_m94c` T1）：41 块文档进入分屏 → 源码侧滚动到块 20（scrollY=952）→ 预览**跳到最后一块**（top=40），`pollSrcScroll` 返回 `idx=40, frac=0.13`（应为 20）。
- **根因（实证，数字全部吻合）**：`pollSrcScroll`（editor.html:5623）
  ```js
  var probe = window.scrollY + Math.min(48, (window.innerHeight||800)*0.08);
  ```
  `probe` 用**绝对坐标**（scrollY+48），而 `yOf()` 返回 `getBoundingClientRect().top` 是**视口相对坐标**。scrollY=952 时 probe=1000，二分条件 `yOf(starts[mid]) <= probe` 等效于「绝对y ≤ 1952」——文档尾块（绝对 y≈1944）也被判入 → idx 饱和到文末。**scrollY 越大偏差越大；scrollY=0（回顶）时 probe 恰好等于正确值，所以回顶同步看起来正常**（C5 PASS 的原因）。
- **对照**：光标跟随分支（cv=true）全部使用视口相对坐标 → 完全正常（T2 top=30 精准）。即「边写边看」场景无恙，「拖滚动条浏览」场景失准。
- **修复方向**：`probe` 去掉 `window.scrollY`（一行）：`var probe = Math.min(48, (window.innerHeight||800)*0.08);`；`frac` 的 `(probe-y0)` 随之自动修正。
- **影响**：用户重点问的「拉动滚动条双屏是否同步」——同步链路在（160ms、双向收敛稳定 T5），但中后段定位错块，实际等于**滚动同步在长文档中后段不可用**。

### SYN-2【P3】预览侧 DOM 未锁定可编辑性，键盘输入可污染显示

- **复现**（T3）：分屏右侧预览 focus 标题 → `execCommand insertText` → 文本直接进入 h1 DOM（`contenteditable="plaintext-only"` 仍在渲染块上）。
- **实际表现**：raw/`__lastPreviewMd` 不变（内容无损坏），但预览显示被污染，且左侧下一次编辑推送 `setPreviewContent` rebuild 后污染消失（自愈）；期间用户可能误以为「预览也能编辑」。
- **修复方向**：`setPreviewMode(true)` 时对 `#editor` 设 `contenteditable=false`（或 CSS `user-modify`/输入拦截），退出时还原。

### SYN-3【P3·设计现状】滚动同步单向：拉预览滚动条源码不动

- **实测**（C9）：拖预览滚动条 +600px，源码 scrollY 纹理不动（1568→1568）。
- **代码事实**：`_poll_sync_scroll` 只轮询 `_view_src`；预览侧无任何滚动上报。
- **竞品参照**：VSCode 预览与编辑器双向同步；MacDown 双向；Typora 无分屏形态。
- **建议**：属产品决策——「预览→源码」反向映射需要预览块 ↔ 源码行对应（`scrollPreviewToBlock` 的逆运算），成本中等；若分屏定位为「左边写右边看」，单向可接受，建议至少在文档中说明。维持现状可接受，登记待议。

### OBS-1【P3·观察】源码模式下应用层「撤销」不生效

- **实测**（B4）：源码模式输入文本后调用 `window.cmd('undo')`，内容无变化（undo 前后尾 14 字符一致）。
- **说明**：`Cmd+Z` 键盘撤销走 Chromium contenteditable 原生撤销栈，未在本轮程序化验证（需人工确认）；本条仅指**工具栏/编辑菜单的「撤销」按钮**（走应用层 `window.cmd('undo')`）在源码模式无效。
- **建议**：人工验证原生 Ctrl+Z；若原生有效，让「撤销」按钮在源码模式转发 `page().triggerAction(Undo)` 即可。
