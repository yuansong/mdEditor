
| 断言 | 说明 |

## 三、缺陷清单

### FMT-1 【P1】行内代码承载叠加格式：格式不生效 + 后续操作范围错位

**最高优先 —— 既是视觉错误，又会污染源码。**

**复现步骤（引用块，最小用例，已实测）**

```
1. 建立引用块：> 引用块内的文字内容
2. 全选文字 → 点「行内码 </>」    → 源码变为 > `引用块内的文字内容`
3. 全选文字 → 点「删除线 S」      → 源码变为 > `~~引用块内的文字内容~~`
4. 观察界面：删除线未生效，显示为字面 `~~引用块内的文字内容~~`
5. 再选部分文字 → 点「链接 🔗」 → 输入 URL → 确认
```

**预期与实际**

| | 内容 |
|---|---|
| 预期 | `[引用块内的文字内容](https://ex.com/doc)` |
| 实际 | `[引用块内的文字](https://ex.com/doc)内容` ← 最后 2 个字被排除在链接外 |

**根因（实证，`tests/_m82.txt`）**

```
③ 加删除线后  渲染明文 = "~~引用块内的文字内容~~"   长度 13（应为 9）
   html = <blockquote><code>~~引用块内的文字内容~~</code></blockquote>
   code=True   del=False        ← 核心：<del> 元素根本没有生成
```

按 Markdown 规范，**行内代码内部不解析任何标记**——所以存储 `` `~~内容~~` `` 本身是正确的。问题出在编辑器的**渲染态交互模型**：

1. 第 3 步把 `~~` 写进了 `` ` `` 内部 → 界面把它当作代码文本**字面显示**，长度从 9 变成 13，且**没有 `<del>`**；
2. 后续所有操作（`applyFloatAction`，`editor.html:7045`）按「渲染明文偏移」经 `mapPlainToRaw` 映射回源码；
3. 用户按所见选 9 个字符，实际选到的是 `~~` + 7 个汉字；经过边界吸附（`editor.html:7073-7088`）剥掉 `~~` 后，只剩 7 个字参与包裹 → 链接少包 2 个字；
4. 之后的加粗/斜体进一步把 `**`、`*` 插入 bereits 错位的区间，最终插入链接文本内部：

```
`~~**[引用块内的文**字](https://ex.com/doc)内容~~`   ← 已损坏，不可恢复
```

**对照实验（排除其它嫌疑）**

| 场景 | 结果 |
|---|---|
| 干净状态直接加链接 | ✅ `[引用块内的文字内容](url)` |
| 先加删除线（无行内码）再加链接 | ✅ `~~[引用块内的文字内容](url)~~` |
| 单层嵌套（bold/strike/mark/code 任一 + 链接） | ✅ 全部正确 |
| **先加行内码再叠加** | ❌ 唯一触发条件 |

**影响范围**：H1 标题、引用块 100% 复现；列表项在本次用例中因选区方式（选中 li 整个内容节点）侥幸规避了**范围错位**，但第 3 步同样会产生字面 `~~` 与格式不生效，**属同源问题，需一并修复**。

**优化建议**
1. **推荐（阻断）**：在 `applyFloatAction` 中检测到映射区间落在同一个 `<code>` 元素内时，**拒绝应用**并提示「行内代码内不支持叠加行内格式」——与已实现的「不支持跨行/跨项应用行内格式」（`editor.html:7092`）同款守卫，改动极小、语义一致。
2. **备选（置灰）**：选区位于 `<code>` 内时，浮动工具栏除「清除格式」外的行内格式按钮置灰不可点。
3. 不推荐「自动把 `~~` 写到 `` ` `` 外层」——会与 CommonMark 规范冲突且行为不可预测。

> **✅ 修复记录（v3.31.2，2026-09-29）**：按推荐方案 1 落地——`applyFloatAction` 开头新增 `<code>` 相交守卫（`intersectsNode` 遍历块内 `code`，比 `closest` 多覆盖「列表整项选区」起点为 li 元素的场景），命中即提示并放弃；`code`（码壳 toggle 取消）与 `clearfmt`（连壳清除）两动作放行，与建议语义一致。回归 173/173。

### FMT-2 【P2】链接不支持 toggle 取消，重复点击产生嵌套垃圾

**复现步骤**：任意容器选中一段文字 → 点「链接 🔗」输入 URL 确认 → **再次选中同一段** → 再点链接、确认。

**预期与实际**

| | 内容 |
|---|---|
| 预期 | 取消链接，回到裸文字 |
| 实际 | `[[引用块内的文字内容](https://ex.com/doc)](https://ex.com/doc)` |

**覆盖范围**：H1 标题 / 列表第 1 项 / 列表第 2 项 / 引用块 —— **4/4 全部复现，100%**。

**根因**：其余 6 个动作走 `wrapSelection(marker)` 的统一 toggle 判定（`editor.html:7113-7114`），而链接走独立分支 `openLinkPop → applyLinkTo`（`editor.html:7101`、`7192-7200`），后者无条件在 `[off, off+len)` 外再包一层 `[](url)`，**没有「已包裹则剥离」的判定**。

**连带影响**：这是列表位点「逆序还原失败」的**唯一原因**——随机序列中链接出现一次，逆序时无法取消，导致最终残留 `- **[第一项内容文本](url)**`。

**优化建议**：链接与其他动作对齐，采用同一 toggle 判定——检测到选区紧邻 `[` 与 `](url)` 时改为**移除链接**（或弹出「编辑 / 移除链接」），而非再套一层。

> **✅ 修复记录（v3.31.2，2026-09-29）**：`action==='link'` 分支增加 toggle 判定——先把映射区间尾部可能带入的 `](url)` 收尾剥出（`plainToRawOffset` idx===L → n.re 语义），再判定「区间左邻恰为 `[`」→ 整壳 `[文字](url)` 剥离还原裸文字并提示「已移除链接」；同时 MKS 边界吸附收缩循环支持链接尾巴剥离（含嵌套 `[` 定位），4 容器逆序还原全部通过。回归 173/173。

### FMT-3 【P2】清除格式（T×）对链接、以及行内代码内标记无效

**复现步骤与实测结果**

| # | 场景 | 操作前 | 点「T×」后 | 判定 |
|---|---|---|---|---|
| 1 | 单独加粗 | `> **引用块内的文字内容**` | `> 引用块内的文字内容` | ✅ 正常 |
| 2 | 单独高亮 | `> ==引用块内的文字内容==` | `> 引用块内的文字内容` | ✅ 正常 |
| 3 | 单独行内码 | `` > `引用块内的文字内容` `` | `> 引用块内的文字内容` | ✅ 正常 |
| 4 | 加粗+高亮 | `> **==引用块内的文字内容==**` | `> 引用块内的文字内容` | ✅ 正常 |
| 5 | **单独链接** | `> [引用块内的文字内容](url)` | **完全未变** | ❌ |
| 6 | **行内码+删除线** | `` > `~~引用块内的文字内容~~` `` | **完全未变** | ❌ |
| 7 | **加粗+链接** | `> **[引用块内的文字内容](url)**` | **完全未变** | ❌ |

**根因**
- **场景 5/7**：`clearSelectionFormat`（`editor.html:7135`）向外吸附标记的字符集为
  `var markerChar = /[*_~`$=]/;`（`editor.html:7153`）——**不含 `[` 和 `]`**，链接外壳无法被纳入待清除区间，因此链接原样保留。这是纯粹的漏配。
- **场景 6**：与 FMT-1 同源——标记位于行内代码内部，对渲染层而言已是代码文本，不是格式。

**优化建议**：`markerChar` 补上 `[`、`]`，并在替换规则中增加「链接段落 → 保留纯文字」的处理；场景 6 随 FMT-1 一并解决。

> **✅ 修复记录（v3.31.2，2026-09-29）**：`clearSelectionFormat` 吸附字符集扩为 `/[*_~`$=\[\]\(\)]/`（补 `[ ] ( )` 四字符）；针对链接增加「闭合尾巴吸附」——区间含未闭合 `](url…` 时右端补齐到配对 `)`。场景 5/7（链接、加粗+链接）与场景 6（行内码内标记，随 FMT-1 守卫 + T× 连壳清除）全部通过。回归 173/173。

## 五、优先级与排期建议

| 编号 | 优先级 | 问题 | 修复成本 | 理由 |
|---|---|---|---|---|
| **FMT-1** | **P1** | 行内代码叠加格式 → 格式不生效 + 源码被污染不可恢复 | 低（一个守卫分支） | 唯一会造成**源码结构性损坏**且用户难以自救的问题；与已有的「跨行守卫」同款写法，可直接套用 |
| FMT-2 | P2 | 链接无法取消 → `[[x](u)](u)` 嵌套 | 低（补一个 toggle 判定） | 100% 复现、4 容器全覆盖，是「逆序还原失败」的唯一原因；与 FMT-1 同批修 |
| FMT-3 | P2 | 清除格式清不掉链接 | 低（正则补两个字符） | 「T×」是用户对「格式错了」的最后自救手段，失效会让用户只能手动改源码；随 FMT-1/2 一并处理 |

**建议批次**：FMT-1 + FMT-2 + FMT-3 三个均为小改动且同属 `applyFloatAction` 链路，**建议合并为一个「行内格式卫生批」一次性处理**，并可复用 `tests/_m81_linefmt2.py` 作为回归基线（修复后应达到 173/173 通过）。
