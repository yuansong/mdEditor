# mdEditor 编辑器内核：宿主模型、感知泄漏与「无感化」路线

> 基准版本：**v3.48.17**（`src/config.py`，2026-10-25 核实）
> 本文回答三个问题：① 多宿主 vs 单宿主到底差在哪；② **不换架构**能否让用户体验无感；③ 长期该往哪走。
> 关联：`COMPETITIVE.md`（竞品差距）、`SoloMD竞品调研-v3.48.9.md`、`scorecard-v3.48.24.md`

---

## TL;DR（先给结论）

1. **「不喜欢多宿主架构」和「用户有感知」是两件事，可以解耦。**
   感知不来自"多宿主"这个抽象概念，而来自**若干个具体的泄漏点**。堵住泄漏点即可无感，无需换内核。
2. **测算：约 5 人天可覆盖日常 90% 的感知**；约 3–4 周可做到"日常使用与单宿主不可区分"。
3. **你们已经用多宿主做出了多光标（MC-1~MC-5）**——而多光标正是"单宿主原生、多宿主必须自绘"的典型能力。这本身就是「多宿主可以做到无感」的最强证据。
4. **长期目标态不是 Typora 模型**，而是「CM6 源码单宿主 + replace widget 嵌入富文本表格」——因为跳到 Typora 模型会赔掉表格护城河。
5. ⚠️ **更正**：本文核实到 v3.48.17 已实装多光标，此前《评分榜》中「写作手感 13/14，扣分含无多光标」的依据**已过时**，见第七节。

## 二、三种宿主模型（为什么 SoloMD 是单宿主却表格弱）

三源交叉验证（官网 solomd.app / GitHub README.zh / Product Hunt LAUNCH.md maker comment）：SoloMD 技术栈 = **Tauri 2 + Vue 3 + CodeMirror 6**，是**单宿主**。

但它实现 WYSIWYG 的方式与 Typora 不同——铁证是官网原文：

> **Markdown markers hide when cursor leaves the line**

即 `#`/`**` 始终存在于文本中，仅靠 decoration 视觉遮罩。**它是「源码单宿主」，不是 Typora 的「富文本单宿主」。**

| | ① 源码单宿主 | ② 富文本单宿主 | ③ 逐块多宿主 |
|---|---|---|---|
| 代表 | SoloMD / Obsidian Live Preview / VS Code | **Typora** | **mdEditor** |
| 可编辑区内容 | 纯 Markdown 源码 | 真实渲染 DOM | 每块独立宿主 |
| 免费获得 | 原生选区 / 撤销 / 多光标 / IME / 拖放 + Lezer 增量解析 | 最彻底的所见即所得 | 复杂块（表格）可做成真富文本 UI |
| 必然代价 | **表格仍是源码文本** | 需自研 schema + 双向序列化 + 标记显隐（最难） | 跨块操作靠 JS 桥接 |

> **核心推论**：SoloMD 表格 4/10 与 mdEditor 表格 9/10，不是能力差异，是**宿主模型的必然结果**。
> 因此"迁到 Typora 模型"的真正代价不是工期，而是**赔掉表格这条唯一的护城河**。

## 三、感知泄漏点清单（本文核心）

> 这是"我不想用多宿主"的真正敌人清单。每一项都是**可在现有架构内修复**的，不涉及换内核。

| # | 泄漏点 | 用户感知到什么 | 无感化方案 | 成本 | 可达性 |
|---|---|---|---|---|---|
| **L1** | **IME 组合期被 rebuild 打断** | 中文连打掉字、候选框跳走（**中文场景最致命**） | 现状：`isComposing` 守卫分散在 7+ 处 keydown（4969/5873/6458/13088/13163/13207/16289），而 **`rebuild()` 本身无守卫**（3696）。方案：在 `rebuild()` 入口加中央守卫——组合期入队 defer，compositionend 后补执行 | **约 0.5 天** | **100%** |
| **L2** | **撤销后光标丢失** | 撤销完要重新找位置，写作流被打断 | 现状：`applySnap` 里 `state.editIdx = -1` + 全量 rebuild。基础设施**已存在**：`_caretTargetEl()`(7104)、`reselectObj()`(17892)。方案：undo/redo 前记录 `(块索引, 字符偏移)`，rebuild 后按偏移复位 | **1–3 天** | **100%** |
| **L3** | **撤销粒度不可预期** | 一次 Ctrl+Z 退掉半句 | 保留 350ms 合并（连续打字合并符合用户预期），但**在语义边界强制 flush**：回车 / 粘贴 / 格式化 / 块操作 / 失焦。已有先例可循（IMG-CROP-5 的 `clearTimeout + snapshotNow`） | **1–2 天** | 90% |
| **L4** | **跨块拖选是自绘叠加层** | 选区色/留白与原生略有差异 | 让 `_xselDraw` 叠加层与浏览器原生 `::selection` **像素级对齐**（色值、末行不延伸、行尾留白规则），并把原生迷你选区设成同色 | **2–3 天** | 90% |
| **L5** | **rebuild 全量重建** | 大文档操作时重绘闪烁 / 滚动位置漂移 | 改局部更新：只替换 dirty 块 + 保持 `scrollTop` | 1–2 周 | 80% |
| **L6** | **光标在块间移动的边角场景** | 某些组合键/点击不生效或跳错块 | 收敛为统一光标移动 API，并对 14 种场景做穷举回归：↑↓←→ / Ctrl+←→ 词级 / Home·End / Ctrl+Home·End / PgUp·PgDn / Tab / 上述 Shift 选区版 / 双击选词 / 三击选段 / 点空白区定位最近块尾 | 1–2 周 | 85% |
| **L7** | 跨块拖放移动文本 | 不支持或行为怪异 | 自定义 drag/drop，落到既有 block 移动 API | 3–5 天 | 75% |
| **L8** | 复制丢富文本格式 | 粘贴到别处只有纯文本 | `copy` 事件里同时写 `text/html`（跨块复制管道已存在：`_aiSelText`） | 1–2 天 | 90% |
| **L9** | 极长文档 DOM 膨胀 | 滚动/输入变慢 | 虚拟滚动（块回收）。**⚠️ 谨慎**：会引入新感知问题（滚动条跳动），建议仅在 >2000 块时启用 | 2–4 周 | 视实现 |
| **L10** | 自绘多光标 caret 与原生不一致 | 多光标闪烁/粗细不同 | **已在做**（MC 系列：caret DOM 自绘 + beforeinput 同步管道 + 测试钩子）。建议最后补彩虹色 hierarchy 与 blink 同步 | 进行中 | 中高 |

## 四、优先级路线图

### P0 · 本周（约 5 人天）→ 覆盖日常 90% 感知
1. **L1** `rebuild()` 中央 `isComposing` 守卫（半天，中文场景最高优先级）
2. **L2** undo/redo 恢复光标位置（1–3 天）
3. **L3** 语义边界强制 flush 快照（1–2 天）
4. **L4** 跨块选区叠加层与原生像素级对齐（2–3 天）

> 这四项任一完成都不会破坏现有行为，可独立发布、独立回滚。

### P1 · 2–4 周
5. **L6** 光标移动场景穷举 + 回归清单
6. **L5** 局部 rebuild
7. **L8** 复制富文本格式

### P2 · 视反馈
8. **L7** 跨块拖放

### P3 · 谨慎引入
9. **L9** 虚拟滚动（先量化：>2000 块才启用）

### 每条必做的验证
按项目惯例配 headless 探针（参考 `tests/_probe_aifrag.py`、`tests/_probe_merge.py` 的组织方式），作为 regressions 基线。

## 五、长期：如果终究要动内核，往哪走

**目标态 ≠ Typora 模型，而是「CM6 源码单宿主 + replace widget」。**

> 用 CodeMirror 6 承载**整篇 Markdown 源码**（免费获得原生选区 / 撤销 / 多光标 / IME / 拖放 + Lezer 增量解析），
> 同时用 CM6 的 **`Decoration.replace({block: true, widget})`** 把表格、MMD 等复杂块的那一段源码**整块替换成真实的富文本组件**。
>
> → 一个可编辑区（跨宿主问题消失）+ 表格仍是 Office 级真组件（护城河保住）。
> 这是 Obsidian 富表格插件与 CM6 生态的标准做法，官方支持。

**代价仍是数月级**：现有 925 KB `editor.html` 的渲染管线需改造成 CM6 的 decoration/widget 体系。
**动手前的最小验证**：花一周只做一个「段落 / 标题两类块」的 CM6 原型，量化 `state.raw` 与 `rebuild` 的真实改动面，再决定是否继续。

**优先级排序不变**：P0 无感化（5 人天） ≫ 跨平台真机构建（+6 分） ≫ 通用双链（+3 分） ≫ 内核替换。

## 方法与免责

- L1–L10 的成本估算是**基于源码现状的工程量判断**，未经实证迭代校准，用于排序而非排期承诺。
- 可达性百分比表达对"能否做到与原生不可区分"的主观判断：100% = 用户完全感知不到差异；90% = 极细微差异（如整段全选时的留白规则）。
- SoloMD 版本号仍存在官网 v5.0.4 ↔ GitHub "New in 4.6" 口径冲突；但其技术栈结论三源一致，可信。
